# Signed release gate contract

The Ubuntu/Windows client-quality jobs in ci.yml and desktop-release.yml explicitly install the pinned Schema test requirements and run schema-contract-test.py. The desktop packaging jobs depend on those contract fixtures as well as browser-contracts. This CI integration checks the published structures; it does not add a Schema engine to the production verifier or provide production scanner, signing or restore evidence.

This verifier validates evidence supplied by controlled CI. Passing its fixture tests does not mean production scanning, signing, or GA acceptance has occurred. CI must pin the release public key and the independent waiver approval public key. Untrusted artifact authors must not control these trusted CLI inputs.

The six existing path arguments remain required: --artifact, --manifest, --public-key, --signature, --dependency-report, --container-report. A seventh argument, --expected-source-commit, is now required and is a lowercase 40- or 64-character Git commit string, not a path. It must come from trusted release-job configuration or a verified release checkout, never from the candidate manifest or reports. The verifier compares it to the signed manifest sourceCommit; valid signatures and internally consistent reports for a different commit are still rejected. This is an intentional CLI compatibility change and all callers must supply the trusted value. The additional --waiver-public-key argument is required for waived findings. CLI file paths resolve from the caller working directory; manifest paths resolve from the manifest directory and must stay within it. Absolute paths, parent traversal, and direct symbolic link entries are rejected.

The new manifest contract uses schemaVersion 2. It contains lowercase 40- or 64-character Git sourceCommit, canonical UTC createdAt, nonempty files, and exactly two scanReports. A file has path, SHA-256 sha256, and integer bytes. A scan reference has kind (dependency or container), path, and sha256. Every file is hashed. The raw final manifest bytes are signed using Ed25519, binding all fields and both scan report hashes. This intentionally replaces the old subset-based signature contract; release producers must update to schema 2 and sign the complete serialized manifest. Schema 1 is rejected.

Each normalized report has schemaVersion 1, kind, status pass, generatedBy controlled-ci, nonempty scanId, sourceCommit, artifactSha256, canonical UTC generatedAt, positive integer scannedTargets, and an explicit findings array. Its scanner has nonempty name, version, and canonical UTC databaseUpdatedAt. Reports and manifests may be at most 24 hours old; vulnerability databases may be at most 72 hours old. Five minutes of future clock skew is allowed. The generatedBy label alone conveys no trust: authenticity comes from the pinned release signature and report hash. CI adapters must normalize actual scanner output and accurately describe target coverage.

Findings contain id, lowercase severity (critical, high, medium, low, info), and status (open or ignored-with-expiry). Critical/high open findings block release. Missing metadata, unknown severities, self-declared resolved statuses, or missing findings arrays fail closed. Every ignored finding requires a waiver with reason (at least 16 characters), approvedBy, ticket, canonical UTC expiresAt between now and 30 days, and base64 Ed25519 approvalSignature.

The approval signature covers UTF-8 JSON serialized in this exact property order: findingId, severity, reportKind, artifactSha256, sourceCommit, reason, approvedBy, ticket, expiresAt. The approval key must differ from the release key. Approval identity and ticket authorization must be enforced by the independent signing service. A valid cryptographic signature does not by itself prove an actual person approved a ticket.

Manifest size is limited to 1 MiB, report size to 32 MiB, and public keys to 16 KiB. Artifact hashing uses a 1 MiB buffer instead of loading the package into memory.

Run node --test scripts/release/release-gate.test.mjs for positive and tampering tests with temporary locally generated keys. All scanner reports in these tests are fixtures, not results from actual dependency or container scanners.

## Schemas and runtime responsibilities

production-report.schema.json describes normalized scan report schemaVersion 1. release-manifest.schema.json describes release manifest schemaVersion 2. These version numbers identify different documents and must not be interchanged. The Schema definitions cover required properties, primitive types, enums, commit/hash formats, timestamp shape, file/reference structure and the fields required by an active waiver. Validators must support Draft 2020-12 and enable date-time format checking.

The production verifier currently uses manual checks and does not execute a JSON Schema engine or load these Schema files. Passing an external Schema validator does not establish runtime signature/hash checks, equality with the caller expected commit, cross-document identity, physical file containment, time limits, independently trusted approval keys, or authorization. Filesystem existence, canonical signature encodings, raw byte signatures, freshness, severe-finding policy and waiver approval signatures remain runtime checks.

The separate schema-contract-test.py regression uses jsonschema 4.23.0, Draft202012Validator and FormatChecker on the actual published Schema files. Its dependency and command are documented in README.md. Both Schema meta-validation and positive/negative document validation run; this is stronger than checking that field names exist, but it still does not run the production verifier's cryptographic or operational checks.

Trust comes from public keys and expected commit input pinned by the trusted caller, plus a signing service that actually validates scanner execution and source/artifact bindings. The generatedBy field is a descriptive label. Neither that label nor a claimed scannedTargets count proves scanner authenticity or real coverage. A signature only establishes that the holder of a trusted key signed particular bytes; the producing pipeline remains responsible for truthful evidence. Approval identity and ticket authorization likewise require a real approval service.

backup-restore-smoke.mjs writes two synthetic JSON files, archives them, restores them and compares their size and checksum. It checks the successful local fixture round trip. It does not validate a real database or object-store restoration, corruption recovery, point-in-time recovery, production RPO/RTO, or automatic pipeline integration. Those require actual isolated restoration jobs and retained logs. No local fixture test, Schema document, or successful verifier run is by itself evidence that production GA acceptance has passed.
