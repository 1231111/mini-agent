MiniAgent 智能体代码开发能力评估报告

评估对象：D:/AI/miniagent（mini-agent 多模块工程，9 个模块）

评估时间：2026-11-19

评估方式：源码逐项核对 + 构建产物与测试报告实测，不采信既有审计文档的结论，关键项回源码复核

一、总体结论

当前智能体能胜任"有人在旁边审查的生产代码修改"，不能胜任"无人值守交付生产代码"。工具链本身已经是生产级的，卡点全部集中在"改完怎么证明改对了"这一段。

换句话说：定位、读、改、执行这几步的能力足够，验证与审查这两步是空的。前者决定它能不能干活，后者决定它干的活能不能直接合进主干。

四、三个真实缺口

缺口一：完成判定不看执行证据

表现：TaskTodoStore.verifyCompletion(doneWhen, evidence) 支持 file_exists:、media_delivered、note_required、llm_judge: 四种谓词；其余情况只要 evidence 字段非空就放行。

机制：done_when 是一段自然语言契约，没有"跑过命令且退出码为 0"这种可判定的谓词，所以判定只能落到字符串是否为空。

后果：模型写下"已修复并通过验证"、evidence 填一句"已修改 Foo.java"，completed 就成立。审计文档 P1-1 记录的"自证加正则启发式"至今未闭合。

修法：给 done_when 增加 build_passes:<command> 谓词，由 exec_command 的退出码判定，ToolStatus 非成功则拒绝 completed。改动集中在 verifyCompletion 一个方法，不动 DAG 结构。

缺口二：界面上看不到改动 diff

表现：mini-agent-app/src/main/resources/static/ 整个目录检索 diff 零命中；chat 目录下有 markdown 渲染、媒体展示、工具时间线，唯独没有改动视图。

机制：edit_file 只返回 {"success":true,"path":...,"replaced":1}，没有把 oldString / newString 结构化回传，前端拿不到可渲染的差异。

后果：用户审查 agent 的产出只能自己打开文件比对，review 成本被推回给人。这是"能不能托管给 agent 改生产代码"的前置条件。

修法：edit_file 与 write_file 在返回值里带 unified diff 摘要，复用已有的 FileActionJournal 写前记录；前端加折叠 diff 块与 revert 按钮。

缺口三：验证是提示词约束，不是机制

表现：PromptTemplates.VERIFICATION_GUIDANCE 写得到位——"跑一次编译命令、有报错就读报错、定位文件、再编译直到通过"、"无法验证要明确说明原因"。

机制：这段内容是一个 String 常量，拼进系统提示；没有任何一处代码检查它是否被执行。

后果：模型自己判断"没必要编译"就会跳过；越到长会话尾部越容易漏。

修法：改动 .java 文件后按路径推断所属模块，自动追加一次 mvn -pl <module> -am test -Dtest=<受影响类>，把结构化结果写回 evidence。把"要求"变成"默认动作"。

五、其他发现

1. agent_environment 是死工具。该工具在 AgentEnvironmentTool 里完成注册，但不在 CapabilityRegistry.PACKS 的任何能力包内，toolsFor() 永远取不到它。结构化规划模式下它不可达，只有 AgentLoop 直跑全量工具面时才可见。这类"注册了但派发不到"的漂移，建议由 CapabilityRegistry.selfCheck() 一并暴露。

2. 工作区有 6 个未提交改动。包括 GoalCompiler、PromptTemplates、14a-inspector.js 等文件。本报告结论基于工作区当前状态，不是最后一次提交的状态。

六、验证建议

最硬的判定不是读代码，是给它一个真实缺陷。建议投放方式：准备一个跨 3 个文件的 Java 缺陷，明确要求"改完必须让 mvn -pl mini-agent-tools test 通过"，然后观察三件事——

一、它会不会主动跑测试；二、测试失败后会不会读报错再改；三、/api/conversations/{sid}/steps 里有没有留下可核对的执行证据。

这三件事成立，上述缺口的实际影响就从"阻断"降为"风险"；任一条不成立，说明模型侧并没有把提示词里的要求当回事，缺口需要按代码机制补，而不是继续加提示词。

附：评估口径

一、"成熟度"是本次评估给出的相对刻度，不是系统内的既有指标；刻度参照"该环节能否在无人干预下稳定收敛"，90% 以上视为生产级，60%-90% 视为接近，60% 以下视为需要补机制。

二、五维划分（定位、改动、验证、承载、安全）是本次评估的分析框架，不对应代码里的任何模块或类。
