## 已定位的问题

### 1. DAG 编译反复失败，且诊断信息不足

最新 JAR 的真实日志确认：初图 13 错 → 修订 7 错 → 再修订 4 错，最终停止。当前日志只记录错误数量，最终 trace 只保留通用 `PLAN_VALIDATION_FAILED`，没有保留各次完整错误列表及被拒绝的图。本次代理也没有保存模型响应正文，因此无法事后证明这三次错误分别是什么；不能把下面的静态缺陷直接认定为这 13/7/4 个错误的确切组成。

需要优先解决的是编译契约与校验契约的一致性，以及可诊断性。只缩短超时或增加重试次数不能解决计划不合格。

进一步用当前编译类运行纯离线探针，已确认一个具体契约缺陷：[IntentGraphValidator.java:67](D:/AI/miniagent/mini-agent-planner/src/main/java/com/miniagent/agent/planner/IntentGraphValidator.java:67) 建议模型通过 `toolArguments` 声明输入消费者，但 [GoalCompiler.java:735](D:/AI/miniagent/mini-agent-planner/src/main/java/com/miniagent/agent/planner/GoalCompiler.java:735) 的解析器没有接收这个字段，导致模型按建议生成的数据仍被丢弃。

另外，[GoalCompiler.java:474](D:/AI/miniagent/mini-agent-planner/src/main/java/com/miniagent/agent/planner/GoalCompiler.java:474) 的重新规划请求只带原问题和错误报告，没有被拒绝的原图，实际是重新生成整个计划。两次重新规划共花 **66.935 秒**，约占本次总时间的 **71.8%**。探针同时证明完整、精确对应验收条件的非文件回答计划可以通过校验，协议并非必然无解；不能断言上述静态缺陷就是本次 13/7/4 项错误的确切原因。

### 2. 验收证据选错，随后恢复成重复检索

桌面样本第一个节点在约 133.77 秒时成功提交 `todo` evidence，仅 **371 字符**；todo 回执 **3,329 字符**。约 147.32 秒时节点却报：

> 语义验收 evidence 超出完整校验范围，尚未验证；请拆分验证材料

当前源码仍存在对应风险：

- [PlanningLoop.java:762](D:/AI/miniagent/mini-agent-planner/src/main/java/com/miniagent/agent/planner/PlanningLoop.java:762) 调绑定器时将提交证据参数传为空。
- [NodeOutputBinder.java:63](D:/AI/miniagent/mini-agent-planner/src/main/java/com/miniagent/agent/planner/NodeOutputBinder.java:63) 因而可能选中保留的原始 `ToolResult`；消息及 trace 的截断没有约束这份原始材料。
- [StepEvaluator.java:296](D:/AI/miniagent/mini-agent-planner/src/main/java/com/miniagent/agent/planner/StepEvaluator.java:296) 对超过 12,000 字符的证据在本地直接拒绝，尚未调用裁判模型。
- 恢复将此问题归为通用 `EVAL_FAILED`，重新运行查询节点，未优先处理材料绑定和预算问题。

因此本次不能解释成“提交的 371 字符太长”，也不是裁判模型响应慢。超限原始材料的精确长度没有被记录，无法从截为 8,003 字符的 trace 推算。该失败在桌面样本中已复现；最新 JAR 因计划阶段先失败，未动态验证到该分支。

### 3. 机票日期被用于新闻式发布日期筛选

桌面样本第一条 `web_search` 的真实参数包含 `dateFrom=2026-11-15`、`dateTo=2026-11-17`；返回附带“所有候选必须核验原文发布日期”的新闻式策略，其中出现与上海—北京机票无关的航线新闻。

本次是模型显式传入日期筛选，并非已证明由 ISO 日期正则触发。当前服务另有把 query 中任意 ISO 日期当作发布日期窗口的静态风险，见 [WebSearchService.java:520](D:/AI/miniagent/mini-agent-tools/src/main/java/com/miniagent/agent/web/WebSearchService.java:520)。机票的出行日与网页发布日期应有明确语义区分；不能用未来出行日约束网页必须在当天发布。

这会降低搜索质量，增加换关键词和补充检索的机会，但本次没有独立量化它增加了多少秒。

### 4. 上下文和执行协议放大模型往返

新会话开始即携带约 1.46 万输入 token；经过检索，峰值达到约 5.10 万。部分工具返回大段页面和多个来源，后续调用重复携带。单次 AgentLoop 模型调用达到 41.74 秒。

本次节点工具面是 20 个工具，不能描述为“传了全部工具”。应在保留来源和完整验收依据的前提下，使用有类型、受预算约束的航班数据、引用和证据包，减少大段原始页面持续进入后续模型调用。

### 5. 性能台账存在盲区

[AgentLoop.java:2323](D:/AI/miniagent/mini-agent-planner/src/main/java/com/miniagent/agent/core/AgentLoop.java:2323) 记录工具结果时传入耗时 0；另一条 pipeline trace 路径也如此。路由、编译和部分验收调用没有独立 trace 用时。本次最新任务实际耗时 93 秒、全在模型调用，但业务 summary 无法准确解释这段时间。

需要同时记录 wall-clock、每次模型调用、队列等待、工具 handler、工具失败、验收和修订，避免只看成功工具或执行阶段 LLM 的累计值。

## 修复优先级

1. **P0：修复编译协议和校验协议的不一致。** 保留每次被拒绝的计划、稳定错误码、节点/字段及修订反馈，确保修订请求能看到原图，解析器接住提示词允许生成的字段。
2. **P0：修复 DAG 证据传递与恢复分类。** 用明确的提交记录、来源引用和工具结果关联构造受预算约束的证据；材料超限先整理/拆分验收，避免重复执行已成功的查询。不能通过静默截断或放松验收来掩盖问题。
3. **P1：分离出行日期和来源发布日期。** 避免机票查询套用新闻时间窗口；为搜索结果和票价提供结构化来源与核实状态。
4. **P1：补齐真实计时，再缩减模型关键路径。** 控制计划长度、无效修订、页面上下文及重复模型往返。动态票价页抓不到时应有明确停止和降级交付规则。

本次没有实施这些修复，也没有得出“最新版本已满足生产级机票查询”的结论。界面没有最终航班卡片，首先是后端没有交付已验收答案；这两次样本没有证据表明卡片渲染是主要瓶颈。
